# VMM 对话数据提取白皮书

副标题：一套经受过脏场景、异常场景、跨模型场景反复拷打之后，仍然能稳定产出可写回记忆摘要的提取流程规范。

版本修订说明（2026-03-27）：

1. 本文保留原有提取经验结论。
2. 当前插件实现已经把旧术语 `turn_outline` 收敛为结构化 `timeline[]`。
3. 阅读本文时，请把文中的 `turn_outline` 统一理解为当前 payload 里的中间过程 `timeline[]`。
4. 当前管理入口已经收敛到 `/vmm-setting`，本文里关于旧 `/vmm-*` 文本命令污染的讨论应视为历史背景，而不是当前运行时设计要求。
5. 当前普通对话链已经新增完整画像 bundle 的隐藏 system 注入；它属于稳定背景上下文，不属于本文讨论的“显式可见记忆包裹”。

这不是一份“看起来很对”的架构稿，而是一份已经被大量正常测试、非正常测试、用户中断测试、模型切换测试、ASK 工具测试、命令污染测试反复校验过的实战文档。

本文只讨论一件事：

如何从宿主 AI 工具的真实对话流里，提取出一份可用于记忆写回的、结构化且尽量不污染语义的数据。

不讨论的范围：

1. 召回策略本身。
2. 向量库或后端记忆服务怎么实现。
3. 真实 writeback API 的鉴权、存储和服务端语义清洗。

本文默认读者是：

1. 想继续维护 `VmmOpenCodePlugins` 的开发者。
2. 想把同样逻辑迁移到 Claude Code、Codex、OpenClaw 或其他宿主的人。
3. 想知道“为什么我们没有走那条看起来更简单的路”的后来者。

## 1. 这套流程到底在解决什么问题

表面上看，我们只是想拿到：

1. 用户问了什么。
2. AI 最终回答了什么。

但真正落地时，现实会把问题复杂化成下面这些：

1. 一轮对话不一定只有一次 user 和一次 assistant。
2. assistant 可能会中途 tool-call、多次过渡输出、重新尝试、报错、被取消。
3. 用户可能会在 assistant 半路回答时打断、补充、改口、撤回。
4. 宿主可能存在 ASK/Question 工具，也可能只有纯文本问题。
5. 宿主可能有主线程、子线程、后台任务、continuation、system reminder。
6. 不同模型、不同 provider 暴露的事件并不一致。
7. 本地控制命令可能物理上也在消息流里，但语义上根本不该进入记忆。

所以真正的问题从来不是“提取最后一条消息”，而是：

如何在充满噪声、分叉、中断、系统回流和宿主特性的对话流里，恢复出一段可信的用户意图轨迹。

我们最终提炼出的答案是：

1. 先做强约束边界。
2. 再做保守收口。
3. 最后做结构化摘要。

这三层一个都不能少。

## 2. 我们最终固定下来的核心原则

这部分是整套方案的总纲。后面的所有实现和测试都只是它们的展开。

### 2.1 只绑定真实主线程，不绑定所有会话

VMM 只跟踪 root session。

原因：

1. 子 task、后台线程、continuation、本地 tool 回流，并不代表新的真实用户轮次。
2. 如果把它们也纳入记忆状态机，系统很快会开始写入脏数据。
3. “看起来像 assistant 又说了一段话”不等于“这是一段用户要长期记住的知识”。

结论：

1. 记忆状态机必须绑定用户真正发起的顶层会话。
2. 后台线程可以影响当前轮状态，但不能自己成为一条独立记忆。

### 2.2 收口不能依赖单一事件

最危险的错误经验之一，就是把某个宿主暴露出来的“看起来像完成信号”的事件，当成唯一真相。

在 OpenCode 里，这个坑对应的就是：

1. 过度依赖 `experimental.text.complete`。

这个事件在某些模型、某些 provider、某些运行路径上可能存在；
但不能假设它永远存在。

结论：

1. `experimental.text.complete` 可以用。
2. 但只能作为文本来源之一。
3. 真正的 finalize 兜底，必须重新读取 `session.messages()`。
4. 只要最终 assistant 已经真实落进消息快照，就应该有机会被提升成 stable answer。

### 2.3 ASK 只能由系统事件认定，不能靠文案猜

普通文本里也可能出现：

1. `1. ...`
2. `2. ...`
3. `请直接回复数字`

如果只靠文本样式判断 ASK，就一定会出现假 ASK 误判。

结论：

1. 真实 ASK 只认宿主原生事件。
2. 比如 `question.asked / question.replied / question.rejected` 这种链路。
3. 纯文本问答一律按普通对话处理。
4. 文本长得像 ASK，也不能自动提升为 ASK。

### 2.4 命令消息必须双层过滤

命令污染是最容易被漏掉的坑。

很多人第一反应是：

1. “/vmm-set 这种命令，当轮别提交就好了。”

这只解决了一半。

因为命令消息物理上仍然可能存在于 `session.messages()` 中。
如果后面又做了一次“从上次提交边界以后重建多轮时间线”，它就会被重新卷进来。

结论：

1. 命令消息在实时 turn 判定时不能提交。
2. 命令消息在后续消息重建时也必须再次过滤。
3. 而且要过滤两类内容：
   - 命令型 user message
   - 它直属的 assistant 回执

### 2.5 用户主动取消的 ASK，不应该强行写入记忆

这也是一个非常重要的边界。

如果 ASK 已经发出，但用户主动取消、dismiss、rejected，说明这次交互没有形成稳定意图。

这时候“不记录”不是能力不足，而是正确的数据清洁策略。

结论：

1. 正常完成的 ASK，题目、选项和选择结果应保留。
2. 被用户主动取消的 ASK，不应进入最终记忆摘要。

### 2.6 记忆 payload 不是“对话备份”，而是“语义提炼”

最终提交的 payload 必须有明确职责分工。

我们当前固定的结构是：

1. `user`
   - 只放首问。

2. `assistant`
   - 只放最终答案。

3. `timeline`
   - 只放中间轨迹。
   - 包括：
     - 后续用户补充
     - 中间 assistant 是否回答过
     - 真实 ASK 的题目、选项和用户选择

4. `recent_turns`
   - 当前对外提交固定为空数组。
   - 本地可以保留，但不跟 writeback 正文混用。

这套分工的意义是：

1. 避免把每轮提交做成“迷你聊天备份”。
2. 避免历史全文越来越长。
3. 让后续服务端语义模型更容易识别：
   - 首问是什么
   - 中途发生了什么
   - 最终答案是什么

## 3. OpenCode 版本的完整提取流水线

这一节只讲“数据提取”，不讲召回、不讲 API。

### 3.1 入口层：识别这是不是一条真实用户输入

OpenCode 里，第一件事不是看文本，而是看这条消息是否来自真实顶层交互。

当前实现的关键点在 `src/plugin.ts`：

1. `isRootSession`
2. `registerRootSession`
3. `isTopLevelUserMessage`
4. `isInternalContinuation`

入口层要做 4 件事：

1. 判断当前 session 是否是 root session。
2. 判断这条消息是否是用户真正发起的顶层消息。
3. 判断它是不是管理面之外的真实聊天输入。
4. 判断它是不是内部 continuation。

如果这里边界放松了，后面所有提取质量都会塌。

### 3.2 分流层：管理交互和普通对话分开

当前实现已经不再依赖旧 `/vmm-*` 文本命令。

现在的原则是：

1. 管理交互统一收敛到 `/vmm-setting` TUI 控制中心。
2. 普通聊天链只接收真实对话输入。
3. 因此“命令文本进入后续多轮提取”的历史问题，在当前设计里已经被入口形态消掉了。

### 3.3 状态层：一轮对话不是只有 activeTurn

单一 `activeTurn` 的模型不够用。

OpenCode 里的真实状态至少需要分成三类：

1. `activeTurn`
   - 正在进行中的真实轮次。

2. `sealedTurns`
   - 已经拿到稳定 assistant，但还没真正 finalize/writeback 的轮次。

3. `awaiting_followup`
   - 已发起 ASK，但仍在等待用户补充或选择的轮次。

为什么需要 `sealedTurns`：

1. 用户可能在上一轮刚稳定时，立刻输入新任务。
2. 如果还只有 `activeTurn`，新 turn 一创建，旧 turn 就没地方放了。
3. 结果会发生“明明已经回答完却被下一条用户消息吞掉”的问题。

为什么 ASK 不能只是一个 boolean：

1. 用户可能关闭程序后再回来。
2. 用户可能几分钟、几小时后才继续。
3. 所以 ASK 不是“短定时器等待”，而是“可恢复挂起态”。

### 3.4 收口层：稳定 assistant 的保守判定

收口是整套系统最脆弱、也是最关键的一层。

我们最终采取的是“多信号并联 + 保守提交”的策略。

当前稳定 assistant 的来源有两条：

1. 实时来源：
   - `message.updated`
   - `experimental.text.complete`

2. finalize 兜底来源：
   - `session.messages()`

具体策略是：

1. assistant 实时输出时，先记录 `lastText / lastMessageID / lastFinish / lastCompletedAt`。
2. 如果实时链路已经足够完整，就可提前形成 stable snapshot。
3. 如果实时链路不完整，到了 finalize 阶段，再从 `session.messages()` 重建主线程窗口。
4. 只要窗口里存在成功完成的最终 assistant，就可以提升为 stable assistant。

这个设计直接解决了一个宿主无关的大坑：

1. 不同模型、不同 provider 的“完成事件”暴露并不一致。
2. 但只要消息快照 API 还在，就不该整条写回链静默瘫痪。

### 3.5 ASK 层：只认真实 question 事件

OpenCode 的 ASK 提取，现在已经完全建立在原生事件上：

1. `question.asked`
2. `question.replied`
3. `question.rejected`

处理方式：

1. `question.asked`
   - 缓存题目、选项、requestID。
   - 标记 turn 进入 `awaiting_followup`。

2. `question.replied`
   - 缓存用户答案。
   - 解除 `awaiting_followup`。
- 把 ASK prompt 和 user answer 作为 timeline event 进入后续 `timeline[]`。

3. `question.rejected`
   - 直接把该 follow-up 视为 cancelled/dropped。
   - 不允许它再长期挂在 collecting 状态里。

这里还有一条很关键的经验：

1. ASK 内容不能后追加到时间线末尾。
2. 必须和普通 user/assistant 消息一起，按真实发生顺序合并。
3. 否则会破坏因果轨迹，变成毒数据。

### 3.6 提取层：从 `session.messages()` 重建这次提交的真实边界

这是 OpenCode 版本真正的精华部分。

提取不是简单地：

1. 取当前 turn 的第一条 user
2. 取当前 turn 的最后一条 assistant

真正做的是：

1. 找到上次已提交 assistant 的边界。
2. 从这个边界之后，重建本轮相关消息窗口。
3. 过滤掉：
   - 内部 continuation
   - 命令消息
   - 命令回执
4. 找到当前最终 stable assistant。
5. 从这段窗口里提炼出：
   - 首问
   - 中间补充
   - 中间 assistant 痕迹
   - ASK 轨迹
   - 最终回答

为什么要记录 `lastCommittedAssistantMessageID`：

1. 如果只靠“上一个成功 assistant”猜边界，跨轮重建会越来越不稳定。
2. 一旦中间有取消、工具态、ASK、命令回执，就很容易误卷历史。
3. 只有“上一次真实提交到记忆系统的 assistant 边界”才是可靠切分点。

### 3.7 摘要层：把多轮轨迹折叠成可写回 payload

最终生成 payload 时，我们只做结构化语义提炼，不做聊天全文归档。

规则固定如下：

1. `user`
   - 永远只取首问。

2. `assistant`
   - 永远只取最终 assistant 回答。

3. `timeline`
   - 只保留中间轨迹。
   - 普通中间 assistant 写成：
     - `assistant: [intermediate response omitted]`
   - 真实 ASK 写成：
     - 问题文本
     - 选项
     - 用户选择
   - 后续用户补充写成：
     - `user: ...`

4. 简单单轮对话
   - `timeline[]` 为空

这套结构的目标不是“看起来完整”，而是“对后续语义模型最友好”。

## 4. 我们一路踩过、并且已经明确解决的问题

这一节非常重要，因为它解释了为什么当前流程看起来比早期方案复杂。

### 4.1 只靠 `session.idle` 或 `experimental.text.complete` 就提交

问题：

1. 很容易把中间态、tool-call 态、异常收口态误判成最终答案。
2. 某些 provider 又可能根本不发 `experimental.text.complete`。

后果：

1. 要么误提交。
2. 要么静默不提交。

解决：

1. 加 settle delay。
2. 引入 stable snapshot。
3. finalize 时再从 `session.messages()` 兜底提升。

### 4.2 只用单一 `activeTurn`

问题：

1. 用户下一句来得太快时，上一轮刚稳定就会被覆盖掉。

解决：

1. 增加 `sealedTurns`。
2. 允许“上一轮先 seal，再异步 finalize”。

### 4.3 ASK 只靠文本判断

问题：

1. 普通长文本里带 `1. 2. 3.` 就会误判成 ASK。

解决：

1. ASK 只认系统 question 事件。
2. 纯文本问题一律交给后续语义层判断，不在插件层伪装成 ASK。

### 4.4 真实 ASK 丢失

问题：

1. 只记 `questionAsked = true` 这种布尔值，不记题目、选项、回答。

解决：

1. 显式记录 `question.asked / question.replied / question.rejected` 的结构化信息。
2. 把题目、选项和回答写入 `timeline[]`。

### 4.5 ASK 顺序被打乱

问题：

1. 先集中收集 ASK，再统一追加到时间线末尾。

后果：

1. 会出现“用户补充发生在 ASK 之前，但重建结果却显示 ASK 在后”的因果错序。

解决：

1. ASK 作为 timeline event，按发生时间参与统一排序。

### 4.6 旧 `/vmm-*` 文本命令污染后续多轮提取（历史问题）

问题：

1. 命令虽然当轮跳过提交。
2. 但它仍存在于消息流里。
3. 后续多轮重建时又被带回来了。

当时的解决：

1. 实时状态机里跳过它。
2. 消息重建窗口里再次过滤它和它的直属回执。

当前实现说明：

1. 旧 `/vmm-*` 文本命令已经移除。
2. 管理交互统一迁移到 `/vmm-setting` TUI 控制中心。
3. 这条污染防护现在主要保留为历史设计说明，不再是当前运行时代码中的专门链路。

这里还要额外注意一个多语言版本的新坑：

1. 显式记忆注入包裹文本会跟随语言切换
2. 如果只认识当前语言包裹，就可能把旧语言轮次留下的包裹文本误当成真实用户输入

所以在多语言版本里，清洗层必须识别所有受支持语言的显式包裹尾标记，而不是只识别当前语言。

### 4.7 用户主动取消的 ASK 该不该记录

结论：

1. 不该。

原因：

1. 取消代表这次选择没有形成稳定意图。
2. 这种信息进入记忆系统，污染大于价值。

### 4.8 provider / model 切换导致收口链失效

问题：

1. 宿主可能一轮一个模型，甚至一轮内部 provider fallback。
2. 如果状态机按模型切，或者只认某一类完成事件，就会很脆。

解决：

1. turn 绑定 `session + epoch + message`，不绑定模型。
2. 模型信息只做日志元数据。
3. 通用真相源是 `session.messages()`，不是某个 provider 特有事件。

## 5. 为什么这套方案对 OpenCode 成立

OpenCode 只是第一个落地主机，不是唯一主机。

这套方案在 OpenCode 里成立，是因为它具备几类非常关键的可用面：

1. root session 与非 root session 有迹可循。
2. 可以拿到消息快照：`session.messages()`。
3. 可以拿到 ASK 生命周期事件：
   - `question.asked`
   - `question.replied`
   - `question.rejected`
4. 可以拿到 assistant 完成态事件：
   - `message.updated`
   - `session.idle`
5. 本地 slash 命令可以在插件层先分流。

本质上，OpenCode 给了我们两类东西：

1. 实时事件。
2. 最终消息快照。

只要宿主同时具备这两类能力，VMM 这种“保守型对话提取器”就能做得很稳。

## 6. 如果迁移到 Claude Code、Codex、OpenClaw，要注意什么

这一节非常重要。不要把本文误解成“只适用于 OpenCode 的特殊技巧合集”。

真正可迁移的是原则，不是某个 API 名字。

### 6.1 你必须先确认宿主有没有“主线程”概念

你要先回答这个问题：

1. 宿主里，什么叫真实顶层用户轮次？

如果这个边界没定义清楚，后面一定会把：

1. 子 agent
2. 工具线程
3. continuation
4. 系统回流

全混进记忆系统。

迁移建议：

1. 找到宿主里最接近 root session 的概念。
2. 如果没有显式 root session，就自己在入口层维护“顶层用户线程注册表”。

### 6.2 你必须确认宿主有没有“最终消息快照”接口

如果宿主只有流式事件，没有最终消息列表，提取会非常脆。

迁移建议：

1. 优先寻找类似 `session.messages()` 的最终快照 API。
2. 如果没有，就自己维护一份 append-only 的本地消息镜像。
3. 但本地镜像必须能区分：
   - user
   - assistant
   - tool
   - system
   - internal continuation

### 6.3 你不能假设所有宿主都有原生 ASK 事件

OpenCode 有 question 事件链，这非常好用。

但其他宿主未必有。

迁移建议：

1. 如果宿主有原生提问/审批/表单事件，优先用原生事件。
2. 如果没有，不要急着在插件层做复杂文本 ASK 判定。
3. 更保守的做法是：
   - 插件层把它当普通中间 assistant
   - 交给后置语义模型去判断是不是需要跨轮绑定

换句话说：

1. 没有原生 ASK 事件时，可以少保留一点 ASK 结构。
2. 也不要用大量假 ASK 误判来污染记忆。

### 6.4 你必须假设模型和 provider 会频繁切换

不要把某个模型特有事件当平台标准。

迁移建议：

1. 状态机不绑定 model id。
2. model/provider 只做日志维度。
3. 收口逻辑尽量依赖：
   - 通用完成态
   - 最终消息快照
   - settle delay

### 6.5 你必须把本地命令和真实对话分开

任何宿主里，只要插件引入了自己的本地控制命令，就一定要有这条纪律：

1. 本地命令不等于记忆语义。

迁移建议：

1. 命令层先分流。
2. 命令消息和命令回执都不要进入后续时间线重建。

### 6.6 你必须考虑用户会主动取消、主动中断、主动删除会话

这类“人类行为噪声”不是边角，而是常态。

迁移建议：

1. ASK 被主动取消时，默认不入记忆。
2. 会话被删除时，清理该 session 的全部本地运行态。
3. 中断和 abort 必须成为状态机一级公民，而不是异常兜底。

### 6.7 你必须把“提取层”和“语义判断层”拆开

这是迁移时最容易犯的错误。

很多人会想在插件里直接做：

1. 用户真实意图判断
2. 话题归并
3. 复杂语义裁剪

这样做会把插件做成一个脆弱的小型规则引擎。

迁移建议：

1. 插件层只做保守结构提取。
2. 后置 LLM 或 API 再做复杂语义清洗、归因和合并。

插件层擅长的事情是：

1. 边界控制。
2. 状态机。
3. 事件排序。
4. 噪声过滤。

插件层不擅长的事情是：

1. 深层语义理解。
2. 多语言细粒度意图推断。
3. 高歧义会话推理。

## 7. 我们建议其他开发者直接照抄的规范

如果你要在别的宿主里实现类似能力，下面这几条建议可以直接当规范用。

### 7.1 必须做的

1. 必须只追踪真实顶层用户对话。
2. 必须区分命令消息和普通对话。
3. 必须把收口做成多信号并联，不依赖单一事件。
4. 必须有一个“上次已提交边界”。
5. 必须在最终提取时从消息快照重建，而不是只信运行时缓存。
6. 必须把最终 payload 拆成：
   - 首问
   - 最终答案
   - 中间轨迹
7. 必须把用户主动取消的未完成交互排除掉。

### 7.2 强烈建议做的

1. 把 ASK 处理成显式状态，而不是临时 boolean。
2. 为 ASK 维护事件时间线，而不是只记最终文本。
3. 为命令污染做双层过滤。
4. 为 aborted / errored / superseded 建独立 dropped reason。
5. 为 session deletion 建立即清理逻辑。

### 7.3 不建议做的

1. 不建议在插件层大量依赖文本启发式来判断 ASK。
2. 不建议把最近几轮原文全文一股脑跟每次提交一起发出去。
3. 不建议把宿主内部 tool 流程当成独立用户意图。
4. 不建议为了“多记一点”而放宽取消、中断、命令这类边界。

## 8. 当前版本的测试建议

一套提取方案，如果没有测试矩阵，就迟早会回退成拍脑袋规则。

至少应该覆盖下面这些场景：

1. 单轮单问单答。
2. 单轮中途补充后再收口。
3. 上一轮刚答完，用户立刻开新任务。
4. 真实 ASK 正常完成。
5. 真实 ASK 被用户取消。
6. 普通文本里出现 `1. 2. 3.` 但不是 ASK。
7. 命令消息后立刻进入真实对话。
8. assistant 中途 aborted，再由用户补充后重新收口。
9. provider 切换。
10. 模型切换。
11. session deleted。
12. internal continuation / system reminder / background 回流。

测试目标不是“证明都能过”，而是及时发现：

1. 脏数据有没有重新混入。
2. 因果顺序有没有被打乱。
3. 哪些边界被某个宿主的新行为打穿了。

## 9. 最后一句话：这套流程真正厉害的地方是什么

不是“它能把聊天记录存下来”。

真正厉害的地方是：

1. 它知道什么该保留。
2. 它更知道什么不该保留。

对于记忆系统来说，数据丢一点通常还能补；
但一旦把错误因果、无效命令、半截 ASK、子线程噪声、异常收口态写成记忆，后面的语义层就会被持续污染。

所以这套流程真正的价值，不在于“抓得多”。

而在于：

1. 用足够保守的边界，
2. 从足够复杂的真实对话流里，
3. 提炼出一份足够可信的记忆候选。

这才是它配得上被迁移到其他宿主插件里的原因。
